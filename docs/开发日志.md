## 一、这个软件要解决什么

一句话：**把"全局代理"拆成"按程序代理"**。

| 场景 | v2rayN / Clash 这类全局软件 | 本软件 |
|---|---|---|
| 谁走代理 | 全机器（系统代理或虚拟网卡模式） | 你指定的那个程序，甚至只是它的一个窗口 |
| 同一个软件多开 | 做不到（一个进程一套设置） | 一个"软件 × 一条线路"一个图标，可同时开多个 |
| 换线路 | 全局切换，影响所有软件 | 只影响绑定了这条线路的那个图标 |
| 内核 | 绑定具体客户端 | 可插拔：sing-box（主）/ xray（兼容旧线路） |

已经落到实处的两个基础：
1. **快捷方式级多实例**——沿用已验证的 Chrome 方案：不同用户数据目录 + 进程级代理参数，
   三个窗口三个出口同时在线、互不关闭。
2. **进程级分流**——sing-box 的 `process_name`（进程名）规则，让"同一个本地端口、
   不同程序走不同线路"成立（本轮已实测，见第四节）。

## 三、步骤 1 交付了什么

核心层（`appproxy/`），不依赖界面，可单独命令行跑通一条完整代理链路：

| 文件 | 职责 |
|---|---|
| `settings.py` | 路径解析（函数式，可用环境变量 `APPPROXY_HOME` 改根目录）、内核查找 |
| `models.py` | 节点模型（统一 vless / vmess / trojan / shadowsocks 四类分享链接）、线路模型 |
| `subscription.py` | 订阅拉取（**强制直连**，不受系统代理影响）+ base64 解码 + 广告节点过滤 + 去重 |
| `singconf.py` | sing-box 配置生成：单线路、自动择优、**分应用调度**（按进程名分流） |
| `xrayconf.py` | xray 配置生成（保留，兼容现有三条 Chrome 线路） |
| `coreproc.py` | 内核进程管理：起、停、状态、配置校验；只杀"命令行里带我们自己的配置路径"的进程 |
| `latency.py` | 节点测速：一次拉起临时内核，每节点一个本地入口并发探测 |
| `registry.py` | 线路注册表 + 节点缓存（纯 JSON，离线可用） |
| `cli.py` | 命令行：`add / update / nodes / select / mode / build / start / stop / status / ping / health` |

关键设计取舍（都是踩过坑之后定的）：

1. **拉订阅必须绕开系统代理**。本机多次出现"系统代理指向已死端口 → 订阅拉取报错"，
   误判成订阅过期。核心层用显式空代理的 opener（直连请求器）。
2. **节点 tag 用内容哈希，不用序号**。订阅按天轮换，序号一变，固定节点的选择就串线了。
3. **构建配置时先实测再筛选**。整份订阅 32 个节点里常常只有三分之一真的通，
   直接全塞进去会让自动择优选中死节点（本轮首次启动就是这么失败的）。
   `build --probe` 先测速，只写通的节点。
4. **收尸按配置路径精确匹配**。本机同时有 v2rayN、Codex 脚本、Chrome 三条线路在跑 xray，
   按进程名杀会误伤，只认"命令行里带这条配置路径"的那个进程。

## 五、步骤 2 交付了什么：应用档案（同软件多代理多图标）

「应用档案」= 一个程序 + 一条线路 + 一份独立数据目录 + 一个图标。
双击图标 = 缺内核就先拉起来 → 带上这份档案的代理参数启动程序。

| 文件 | 职责 |
|---|---|
| `profiles.py` | 档案模型与存储（`profiles.json`）；把「档案 + 线路」翻译成启动命令（Chromium 系走参数，其他走环境变量） |
| `launcher.py` | 快捷方式真正指向的入口：确保内核在跑 → 组命令 → 启动程序 → 自己退出 |
| `icons.py` | 生成 16/24/32/48/64/128/256 七档 `.ico`：底色+大字=哪个软件，右下角标=哪条线路 |
| `shortcut.py` | 生成 `.lnk`（系统 COM 优先、pylnk3 兜底），母版放 `shortcuts\`，两个桌面各投一份 |
| `cli.py` | 新增 `profile add / set / rm / list / show / launch / icon / shortcut` |

### 关键设计：为什么每个档案必须独占一个端口

`process_name` 规则按**进程名**匹配。同一个 exe 开两个实例，进程名完全一样
（`chrome.exe` / `chrome.exe`），内核在规则层面**无法区分**它们。
所以"同一个软件、多个代理、多个图标"不能只靠按进程分流，必须让每个档案连**自己的本地端口**。

两个机制并存、各管一段：

| 机制 | 解决什么 | 例子 |
|---|---|---|
| 档案专属端口 | 同一个 exe 的多个实例各走各的线路 | 三个 Chrome 图标，分别连 10801 / 10803 / 直连 |
| 进程名规则（步骤 1） | 一个端口覆盖一整类程序，不用改程序参数 | Telegram、命令行工具统一走 10803 |

### 三个关键设计

1. **系统代理"借用"而非"霸占"**：开启前先备份原来的设置（本机原本是 `http=127.0.0.1:10888;…`，
   即旧 Chrome 方案留下的），关闭时原样还原。所以它和 v2rayN 不打架，只是临时借道。
   只动 `HKCU`，不需要管理员权限。
2. **托盘状态一眼可读**：图标颜色即状态——绿=全部运行、蓝=系统代理已接管、黄=部分运行、灰=全停；
   悬停标题带 `(2/2)` 计数。
3. **耗时动作全在后台**：起内核、测速、扫描都不占托盘线程，菜单随点随开；同一时刻只跑一个重活，
   避免两条线路抢同一个端口。
4. **单实例锁兼作控制通道**：托盘占住本地端口 10896，第二个实例会自动退出；这个端口同时接受
   `quit` / `ping` 两个指令，所以命令行能叫它优雅退出（`tray --quit`），
   而不用杀进程留下"幽灵图标"。**退出时会先把我们拉起来的内核停干净**，不留后台残留。

## 七、步骤 4 交付了什么：主界面 + 代理开关重做

### 7.1 为什么要重做「启动 / 关闭」

步骤 1–3 里，开关的对象是**线路**（内核 + 端口）。于是托盘菜单上出现了「全部启动 / 全部停止」，
它其实是「把所有内核都预热起来」。这套逻辑和产品卖点是打架的：

| 问题 | 说明 |
|---|---|
| 预热 ≠ 按需 | 用户注册 5 条线路、只有 2 条有软件在用，剩下 3 条白占端口和内存 |
| 与卖点相反 | 产品的核心是"用到才起、用完即走"，全部启动等于退回全局代理软件的常驻模型 |
| 点了没反应 | 串行 `ensure_core`，每条最多等 25 秒；缺配置的线路还要当场拉订阅 |
| 无法表达意图 | 用户想的是"我要用这个软件"，菜单给的却是"我要开这条线路" |

**新语义：开关的对象是软件，不是线路。**

| 动作 | 发生了什么 |
|---|---|
| 启动某软件 | 它要代理 → 只拉起**它那条**线路（约 1 秒，不测速）；它是直连 → 一个内核都不起 |
| 关闭某软件 | 结束它的进程；这条线路没有别的软件在用了 → 内核自己退场；还有别人用 → 内核留着 |
| 软件自己关掉 | 后台每 5 秒扫一次，发现没人用了就把内核回收 —— **不需要用户点"全部停止"** |
| 手动起的内核 | 不受自动回收影响（用户可能要留给系统代理用） |

### 7.2 内核按需化怎么实现的

| 文件 | 职责 |
|---|---|
| `procwatch.py` | 判断「这个档案的程序还开着吗」。Chromium 系按 `--user-data-dir` 精确匹配（同 exe 多开也分得清）；通用程序按 exe 路径匹配 |
| `pool.py` | 内核池。登记「谁为谁拉起了内核」→ 起（不测速）→ 没人用了就回收；只碰登记过的，手动起的不动 |
| `launcher.py` | 启动器改成走 pool，并在启动后**等程序真的出现在进程表**里才退出 |
| `gui.py` / `webui/` | 主界面：本地 HTTP 服务 + 单页 HTML + 窗口外壳 |
| `gui_support.py` | 界面用的小工具：ico→png、按可用节点生成配置 |

三条硬规则：

1. **启动路径上绝不测速。** 测速是独立后台任务，慢也只慢自己。「更新订阅 + 测速」走后台线程 + 任务表，界面轮询进度，任何 HTTP 请求都不会等它。
2. **回收只碰登记过的线路。** 用户手动起的内核（比如要留给系统代理）永远不被自动停。
3. **判活靠进程，不靠内存计数器。** 界面关掉再打开、托盘重启，判断依然正确。

启动完成后还有 60 秒宽限期（`pool.GRACE_SECONDS`）：程序从 `Popen` 到真的进进程表有一两秒空档，这段时间不能被误判成"没人用"，否则刚起的内核会被立刻停掉。

### 7.4 两个界面级的坑（都会导致白屏）

1. **系统代理没跳过本机地址 → 界面自己白屏。**
   本机系统代理是 `http=127.0.0.1:10888`（v2rayN 的）且 `ProxyOverride` 为空。
   WebView2 / 浏览器会把 `http://127.0.0.1:1443` 也送进这个代理，代理不转发本机地址 → 整片白。
   两处都修了：窗口外壳加 `--no-proxy-server`；`sysproxy.enable()` 现在写入
   `ProxyOverride = localhost;127.*;10.*;172.16.*;192.168.*;<local>`，
   保证接管系统代理后自己还进得去。
2. **WebView2 环境创建失败时 pywebview 不报错，只留白。**
   日志里只有一句 `Failed to delete user data folder: 'NoneType' object has no attribute 'BrowserProcessId'`。
   所以窗口外壳改成优先用 **Chrome/Edge 的 `--app` 模式**（无地址栏、无标签页，外观就是独立桌面应用），
   `--native` 才走 pywebview。

| 回收（程序在跑） | GC 未回收，内核留着 |
| 回收（程序关掉） | GC 回收内核，端口释放，登记清空 |
| 关闭按钮 | 程序结束 + 内核释放，一次到位 |
| 手动起的内核 | GC 不碰它 ✅ |

单元测试 **79 项通过**（62 + 步骤 4 新增 17）。

### 7.6 托盘收敛 + 双渠道进设置（按用户反馈调整）

原来的毛病：设置只能「先进主界面 → 再点左下角那个很小的设置按钮」；托盘右键又是
一棵三层树（线路 / 应用 / 系统代理 / 开机自启 / 打开目录），每天用的和一年点两次的
混在一起。

改了两件事：

1. **托盘只留日常动作，顶层 6 项封顶**（另加一行状态标题）

   ```
   分应用代理管家 · 全部运行中（1/1）   ← 点它 = 打开主界面
   ────────────
   打开主界面                            ← 界面已在后台时自动变成「显示主界面（已在后台）」
   设置…                                 ← 直达设置页；界面已开着时变成「设置（切到界面并闪烁提示）」
   ────────────
   启动所有软件
   关闭所有软件（并释放内核）
   ────────────
   系统代理 ▸
   ────────────
   退出
   ```

   砍掉的「线路 / 应用 / 开机自启 / 打开目录」不是删功能，是**退回主界面**：
   设置页里有线路管理（起停、更新订阅+测速）、开机自启、五个目录入口；
   左侧 ＋ 就是程序库。开关对象依然是「软件」，不是线路。

   两个入口的文案会**跟着界面状态自己变**（托盘 6 秒心跳里重建菜单）：

   | 界面没开 | 界面已经开着 |
   |---|---|
   | 「打开主界面」 | 「显示主界面（已在后台）」 |
   | 「设置…」 | 「设置（切到界面并闪烁提示）」 |

   为什么要变：界面开着时这一项不再「开新窗口」，它做的是**切页 + 让已有窗口在任务栏闪**。
   不写清楚，用户点完看不出反应，会以为软件坏了。

2. **设置两个正门，指向同一页**
   - 托盘右键 →「设置…」：主界面没开就直接开到设置页；已经开着就发一条
     `POST /api/view {"view":"settings"}`，界面 1.2 秒内轮询取走 → 切页 →
     提前台 + **任务栏闪烁**（提不上前台时，闪烁是用户唯一能看到的反馈）。
   - 主界面里也有两处：左下角**整行「设置」**（常驻可见，像微信左下角）+ 右上角齿轮。
   - 深链 `#settings` / `#apps`、命令行 `gui --view settings` 同样直达。

支撑这套东西的五个小机制：

| 机制 | 干什么 | 为什么必须这样 |
|---|---|---|
| `gui.port` 路标文件 | 界面把实际端口写下来，退出时删除 | 1443 被别的程序占了会退到随机端口，托盘不能靠猜 |
| `/api/ping` 带 `app` 标记 | 认门：端口上是不是自己人 | 免得把别人占着的 1443 当成自家界面去发指令 |
| 内存信箱 + 取走即清空 | 托盘投递、界面取走 | 否则界面每轮轮询都会把用户手动切走的页面强行拉回设置页 |
| `AttachThreadInput` 抢前台 | 跨进程把窗口提到最前 | Windows 默认不许后台进程抢前台，裸 `SetForegroundWindow` 常被拦 |
| `FlashWindowEx` 闪任务栏 | 提不上前台时的兜底提示 | 点到「没反应」是最伤体验的失败，闪一下成本几乎为零 |

> 坑：`FlashWindowEx` 的返回值是「调用前窗口是否已处于活动状态」，**不是成功/失败**。
> 一开始拿它当返回值判断，窗口正好在前台时会误判成"闪烁失败"，返回给用户的文案就少了一截。
> 现在只要找到句柄、调用不抛异常就算做了。

实测（`tests/live_view.py` + `tests/live_window.py`，2026-10-26 本机）：

| 验证 | 结果 |
|---|---|
| 托盘顶层项数 | 7 行（含状态标题 + 分隔符之外），旧版 8 项且带 4 个二级菜单 |
| 托盘点「设置…」 | 找到已开窗口 → 返回「已切到已打开的窗口（任务栏闪烁提示）」（没有新开一个） |
| 任务栏闪烁 | 按标题找到窗口句柄 + `FlashWindowEx` 调用成功 ✅ |
| 界面真的切页 | 前端回报 `current=settings` ✅；信箱取走即空 ✅ |
| 再切回主界面 | ✅（双向都通） |
| 没有窗口时点设置 | 新起进程，URL 带 `#settings`，直接落在设置页 |
| 接口 + 截图 | 12 项全通过，`docs/主界面.png`、`docs/设置页.png` 已更新 |

## 八、步骤 5 交付了什么：TUN + 需代理清单 + 新用户接线

### 8.1 TUN（虚拟网卡接管）：给「不认代理参数」的程序兜底

前四步的做法是**把代理参数塞给程序**（Chrome 用 `--proxy-server`，其余程序注入
`HTTP_PROXY`/`HTTPS_PROXY` 环境变量）。程序不认这些参数就漏 —— 游戏、部分 Electron 客户端
（聊天、IDE）、后台更新器都属于这一类。

TUN 换个思路：在系统里建一块虚拟网卡，**先把整机流量接住**，再按进程名分流。

| 维度 | 塞参数（主用法） | TUN（本轮新增，高级选项） |
|---|---|---|
| 权限 | 零权限，双击即用 | 需要管理员令牌（建虚拟网卡） |
| 覆盖面 | 只对认参数的程序有效 | 全部程序，认不认参数都跑不掉 |
| 副作用 | 几乎没有 | 个别反作弊会拦；改路由表 |
| 默认状态 | 开 | **关**，用户自己开 |

分流规则（按你 2026-10-26 定下的四条）：

1. **未登记的软件一律直连**（`route.final = direct`）——不越权接管别人的流量；
2. **建过档案、绑了线路的软件**才走它那条线路（按 `process_name` 匹配）；
3. **开 TUN 自动关系统代理**（并记住原状态），关 TUN 时原样还原 —— 两者同时开会绕圈；
4. **不做 kill-switch（断线保护）**，避免内核一抖整机没网。

提权怎么做到「只弹一次 UAC」：装一个**没有触发器**的计划任务（`AppProxyTun`，
`RunLevel = HighestAvailable`），内核由任务拉起。
安装任务那一下要管理员；以后启动只是 `schtasks /Run`，普通权限即可。

**用户要点的东西只有一个：UAC 弹窗上的「是」。** 见 `docs/TUN在哪里点.png`。

第一版这里是让用户「右键以管理员身份运行」，实测发现这是个死路 —— 主界面是
Chrome `--app` 窗口，用户根本没地方右键提权。改成程序自己
`ShellExecuteW("runas")` 拉起一个提权子进程（`python -m appproxy.elevate install`），
用户只需要在弹窗上点一次「是」，之后不再弹。

两个入口都能触发同一段代码：

| 入口 | 说明 |
|---|---|
| 主界面 → 设置 → 「开启 TUN」 | 产品正常路径；点完先 toast 一句「如弹出用户账户控制，请点是」 |
| 桌面「验证TUN（点一次授权）」 | 诊断用（`tools/verify_tun.py`）：配置校验→装任务→起内核→查网卡，跑完弹窗给结论，报告写 `D:\AppProxy\logs\tun-verify.txt` |

UAC 被点「否」时不会报 traceback，而是一句话：*你取消了管理员授权，TUN 没有开启。
想用的话再点一次「开启 TUN」，在弹窗里选「是」即可（只需这一次）。*

> 踩到的坑：sing-box 1.12+ 只要配了 `dns` 段，就必须给 `route.default_domain_resolver`，
> 否则 `sing-box check` 直接 FATAL。第一版就是漏了这个，被真机校验挡下来。
> 另外走代理的进程要用**加密 DNS 且经代理出去**（`detour`），否则解析结果照样被污染。

### 8.2 「明显需要代理的软件」清单（`appproxy/data/apps_need_proxy.json`）

一句话：**内置 32 条**，其中 24 条能按进程名识别（Chrome、Telegram、Discord、ChatGPT、
Codex CLI、Claude、Cursor、Notion、Spotify、Steam 等）；
YouTube / Facebook / Instagram / X / Netflix 这些只有网页版的，留在清单里当说明
（由浏览器那条规则覆盖），不做进程匹配。

设计上有意收得很紧：

* 只按**进程名**匹配，不看路径（同一个 exe 装哪都是同一个程序）；
* 匹配不上就返回 `None`，**绝不猜** —— 宁可少提示，不要乱接管；
* 清单可以**被数据目录里的同名文件整份覆盖**（`appdb update <网址>` 从在线源拉），
  这样以后更新清单不用重新打包。

命中之后做什么：程序库列表里标「需代理」并排到第一屏，**但仍然由用户决定绑哪条线路**。
这个软件绝不替用户选服务商。

### 8.3 新用户接线：三种答案都落到同一条「线路」上

一条线路都没有时，主界面不再显示空白，而是弹接线页（`docs/引导页.png`）：

| 选项 | 适用 | 实现 |
|---|---|---|
| A. 订阅链接 | 机场 / 自建，最常见 | `subscription.load()` → 全部节点 → urltest 自动择优 |
| B. 节点分享链接 | 只有一个节点 | `subscription.parse_uri()` → 单节点 + `mode=single` |
| C. 本地端口 | 机器上已经跑着 v2rayN / Clash | 生成一个 `socks`/`http` 出站指向 `127.0.0.1:<端口>` |

C 是最容易被忽略但最实用的一条：用户往往**已经**有代理客户端，只是想要「按软件分」。
填端口前会先探活，没在监听就直接告诉他"先把你的代理客户端打开"，而不是建一条死线路。

三种方式最终都只产出一样东西：一条 `Line`（线路）+ 它的节点快照。
之后所有功能（按软件启动、系统代理、TUN）走的都是同一条代码路径，**没有为「本地端口」写特例**。

### 8.4 仓库里为什么不带任何线路数据

线路订阅地址里带 token（访问令牌），一旦跟着安装包或仓库发出去，等于把账号公开。
所以这个仓库**不含任何线路数据**：`data/` 是空的，`D:\AppProxy` 整个目录都在
`.gitignore` 里。clone 下来第一次打开，看到的是「先告诉我你的代理在哪」的接线页。

给要自己做发布包的人留了一条命令：

```bat
python -m appproxy.cli cleanup          :: 预演：只打印要删什么
python -m appproxy.cli cleanup --yes    :: 真删：先备份，再清空线路/节点缓存/配置/快捷方式
```

它会：备份 `lines.json` + `profiles.json` 到 `D:\AppProxy\backup-cleanup-<时间>\` →
删掉所有线路、节点快照、生成的配置、生成的快捷方式 → 把档案里的线路绑定改成「直连」。
**不删档案本身**（用户装了什么软件不算隐私）。

发布前逐条对照：`docs/发布前检查清单.md`。

## 九、怎么用

```bat
cd /d <项目目录>

:: ---- 主界面（步骤 4，日常就用这个）----
python -m appproxy.cli gui              :: 打开主界面（默认 Chrome/Edge --app 窗口）
python -m appproxy.cli gui --view settings  :: 直接落在设置页（托盘「设置…」走的是同一条路）
python -m appproxy.cli gui --native     :: 强制用 pywebview 原生窗口
python -m appproxy.cli gui --debug      :: 带开发者工具，调界面用

:: 托盘（常驻入口；默认不预热内核）
python -m appproxy.cli tray
python -m appproxy.cli tray --install   :: 顺便在桌面建快捷方式
python -m appproxy.cli tray --quit      :: 优雅退出（先停内核）

:: 看两个内核在哪、什么版本
python -m appproxy.cli bin

:: 加一条线路（端口不填会自动挑空闲端口）
python -m appproxy.cli add --id airport --name 示例机场 --sub "<订阅地址>" --engine singbox

:: 拉订阅、看节点、测速
python -m appproxy.cli update airport
python -m appproxy.cli nodes airport --region US
python -m appproxy.cli ping airport --top 10

:: 生成配置（--probe = 先实测，只用通的节点）并启动
python -m appproxy.cli build airport --probe
python -m appproxy.cli start airport
python -m appproxy.cli health airport
python -m appproxy.cli stop airport

:: ---- 应用档案（步骤 2）----
:: 建一个"带代理的 Chrome"图标（自动生成图标 + 桌面快捷方式）
python -m appproxy.cli profile add --id chrome-airport --name "Chrome·示例A" ^
    --exe "C:\Program Files\Google\Chrome\Application\chrome.exe" ^
    --line airport --url "https://www.google.com"

:: 再建一个直连的（同一个 exe，第二个图标，互不影响）
python -m appproxy.cli profile add --id chrome-direct --name "Chrome·直连" ^
    --exe "C:\Program Files\Google\Chrome\Application\chrome.exe" --direct

:: 查看 / 改绑定线路 / 重做图标与快捷方式 / 试运行
python -m appproxy.cli profile list
python -m appproxy.cli profile show chrome-airport
python -m appproxy.cli profile set chrome-airport --line beta
python -m appproxy.cli profile icon
python -m appproxy.cli profile shortcut
python -m appproxy.cli profile launch chrome-airport --dry-run

:: ---- 系统级开关 ----
:: 系统代理：接管到某条线路 / 关闭并还原 / 看状态
python -m appproxy.cli sysproxy status
python -m appproxy.cli sysproxy on airport
python -m appproxy.cli sysproxy off

:: 开机自启（默认关，手动开）
python -m appproxy.cli autostart status
python -m appproxy.cli autostart on
python -m appproxy.cli autostart off

:: 扫本机已安装程序（主界面「＋」里的程序库用的就是这个缓存）
python -m appproxy.cli apps scan --limit 30
```

托盘以后**双击桌面的「分应用代理管家」图标**即可，不要从命令行起（工具会话结束会连带回收子进程）。

### 日常怎么用

1. 双击桌面「分应用代理管家」→ 托盘出现（**不会预热任何内核**）
2. 双击托盘图标（或右键第一行）→ 主界面
3. 左侧选一个软件 → 右侧点「启动」→ 它那条线路的内核起来（约 1 秒）→ 程序带着代理打开
4. 用完直接关程序。5 秒内后台发现没人在用，内核自动退场，什么都不用管

要加新软件：主界面点「＋」→ 从已安装程序里挑 → 选它走哪条线路 → 「添加」。
会顺手生成一个带角标的专属图标和桌面快捷方式，以后双击那个图标就直接带着代理打开。

**进设置有三条路，都是同一页**：

- 托盘右键 →「设置…」（主界面没开就直接开到设置页；开着就切过去并跳到最前）
- 主界面左下角**整行「设置」**（一直看得见）
- 主界面右上角齿轮，或地址栏 `#settings`

设置页里管四件事：线路（起停内核、更新订阅 + 测速）、系统代理（接管 / 关闭还原）、
通用（新档案默认线路、开机自启、引擎路径、五个目录入口）。

补充说明：

- 快捷方式指向 `pythonw.exe …\launcher.py --profile <id>`。换解释器或以后打包成 exe 后，
  用环境变量 `APPPROXY_PYTHON` 指定新的解释器，再跑一次 `profile shortcut` 即可重指。
- 浏览器档案强烈建议保留独立的 `--data-dir`（默认就是 `D:\AppProxy\apps\<id>\data`）。
  想让某个档案用你**真实**的 Chrome 配置，加 `--data-dir "<你的 User Data 路径>"`，
  但同一个数据目录同时只能开一个实例。
- 主界面的窗口是个独立的 Chrome/Edge `--app` 窗口，配置目录在 `D:\AppProxy\gui-profile`，
  和你的日常浏览器完全隔离，关掉窗口本地服务就退出，不影响已经开着的代理。

注意：**从工具会话里启动的内核会被回收**（父进程结束时子进程一起被清理）。
要常驻，必须由你自己双击启动（第 3 步的托盘程序会解决这件事）。

主引擎 **sing-box 1.14.4**（GPL-3.0-or-later，GNU 通用公共许可证第 3 版或更高版本），
发行包已放入 `third_party/sing-box/`，含原始 LICENSE 文件。详见
